# 数据库版本管理

> 当前业务目录与分层以 [业务模块开发约定](业务模块开发约定.md) 为准；已新增 V3 命名迁移与 V4 业务入口，新增数据库变更从 V5 起编号。历史 V1/V2 不修改。

新版本使用 Spring Boot 自动执行 Flyway。唯一生效的迁移目录为：
`backend/cdzs-server/src/main/resources/db/migration/`。

迁移使用独立 JDBC 连接，账号仍使用当前项目的 `DB_USER`/`DB_PASSWORD`，不依赖 root 或额外开放 MySQL 系统表权限。业务查询继续使用 Druid 连接池。

- `V1__starter_schema.sql`：基础表、默认租户、角色、菜单及安装标记。
- `V2__example_task.sql`：示例任务表、索引、菜单及管理员授权。
- `flyway_schema_history`：数据库中的执行版本、校验和和执行结果。

## 新项目首次启动

1. 运行 `node scripts/init-env.cjs` 生成本地 `.env`。
2. 启动 MySQL/Redis：`./scripts/dev.ps1 infra`。
3. 启动后端。Flyway 创建表并执行 V1、V2，安装器随后设置初始密码。
4. 后续启动仅执行新增迁移，不会覆盖已修改的账号密码。

MySQL 容器不再挂载 `database/init`。该目录仅保留旧版初始化参考；不要在已有数据库导入它，也不要同时用它和 Flyway 创建新库。`generate-database.cjs` 是旧版生成工具，不用于新增版本。

## 接管此前创建的底座数据库

1. 先备份，确认连接的是独立底座库。
2. 首次升级临时设置 `.env`：`STARTER_BASELINE_EXISTING=true`，或启动参数 `--STARTER_BASELINE_EXISTING=true`。
3. 启动后端。程序检查已完成的安装标记、默认管理员和核心表，再登记版本 1，执行 V2。
4. 确认历史表 V2 执行成功后，将开关改回 `false`。不要把旧库接管开关当成普通初始化选项。

非空库默认不自动 baseline。不属于本底座的数据库应单独设计迁移方案，不能靠开关强行接入。

## 开发下一次数据库变更

1. 新建 `V5__add_task_due_date.sql`，写增量 SQL，例如 `ALTER TABLE example_task ADD COLUMN due_date DATE NULL;`。
2. 同一分支中版本号唯一；多人开发合并时先协调版本号。
3. 在测试库验证：空库全量安装，以及旧版数据库升级。
4. 提交 SQL 与使用该字段的代码，一起发布。
5. 已经执行过的 V1/V2 不允许再修改；修正通过新的 V3/V4 完成。

默认启用校验，禁用 `clean` 和乱序迁移。MySQL DDL 不保证事务回滚；迁移失败时先检查数据库实际结构与备份，修正前不要盲目删除历史记录或执行 repair。

## 回滚约定

自动回滚仅恢复应用镜像，不恢复数据库。因此迁移默认采用向后兼容方式：先加列/表、允许旧代码继续工作，再在后续版本清理。删列、改语义和数据重写必须单独安排维护窗口及恢复方案。

官方依据：[Spring Boot 数据库初始化](https://docs.spring.io/spring-boot/3.5/how-to/data-initialization.html)。
