## 1. 底座包含什么

这是可以直接继续开发业务的独立项目，基于芋道官方精简版，已经配好前后端、数据库初始化和部署脚本。

| 能力 | 当前情况 |
|---|---|
| 用户、部门、岗位、角色、菜单 | 已有页面和后端接口 |
| 按钮、接口、数据权限 | 已有基础能力；新业务仍需接入权限规则 |
| 站内信 | 配置模板后可接入业务发送 |
| 短信、邮件 | 已有渠道、模板与日志管理；需配置自己的服务商账号 |
| 登录、操作、接口日志 | 已有；业务操作日志按场景补充 |
| 字典、参数、文件管理、代码生成 | 已有 |
| 示例业务 | “开发示例 → 示例任务”，含 CRUD、分页、导入导出、权限与数据隔离 |
| 数据库版本管理 | Flyway 自动执行版本 SQL |
| 部署工具 | Docker Compose、Jenkins、升级前备份、应用回滚、数据库恢复工具 |
| 页面样式 | 简洁蓝灰主题、登录页、工作台和公共组件样式 |

工作流、支付、商城、采购等业务不是默认启用的基础功能。Quartz 定时任务默认不启动。上游保留的一些源码或菜单不代表对应功能已经完成部署配置。

## 2. 目录结构

```text
zs_yd/                       # 本地目录也可以叫 cdzs-starter
├─ README.md                 # 项目入口说明
├─ .env.example              # 环境配置模板，可提交
├─ .env                      # init 生成的本地配置，不提交
├─ Jenkinsfile               # 根目录流水线
├─ UPSTREAM.json             # 上游版本记录
├─ backend/
│  ├─ pom.xml                # 后端 Maven 聚合入口，IDEA 导入这个文件
│  ├─ cdzs-framework/       # 公共框架能力
│  ├─ cdzs-module-system/   # 用户、权限、消息等
│  ├─ cdzs-module-infra/    # 文件、基础设施等
│  ├─ cdzs-module-business/ # 新项目业务代码，已注册并接入启动模块
│  ├─ cdzs-module-example/  # 标准业务示例
│  └─ cdzs-server/          # 启动模块和 Flyway 迁移
├─ frontend/
│  ├─ .env                  # 前端公共配置，不含服务端密码
│  ├─ .env.starter          # 本地开发模式
│  ├─ .env.deploy           # 部署构建模式
│  ├─ src/views/business/   # 业务页面与业务组件
│  ├─ src/api/business/     # 业务接口封装
│  ├─ src/                  # 其他页面、接口、主题
│  └─ package.json
├─ deploy/                  # Docker、Nginx、Jenkins 目标、备份恢复脚本
├─ scripts/                 # 启动、初始化与验证脚本
├─ database/init/           # 旧版 SQL 参考，不用于当前首次启动
└─ docs/                    # 使用与开发文档
```

后端入口：`backend/cdzs-server/src/main/java/cn/cdzs/server/CdzsServerApplication.java`。

## 3. 准备开发环境

| 工具 | 本仓库使用要求 |
|---|---|
| Git | 用于拉取和提交代码 |
| JDK | 17 |
| Maven | 3.9.x |
| Node.js | 20.19+，可使用 22.x |
| pnpm | 10.33.0，与 packageManager 一致 |
| Docker Desktop | 启动成功，使用 Linux 容器 |
| Docker Compose | v2，部署节点建议 2.24+ |
| IDEA | 用于 Java 开发；前端可使用 IDEA 或其他编辑器 |

打开 PowerShell，逐条确认：

```powershell
git --version
java -version
mvn -v
node -v
pnpm -v
docker version
docker compose version
```

`mvn -v` 输出中的 Java 版本也应为 17。只在 IDEA 选择 JDK，不一定会改变命令行 Maven 使用的 Java。

没有 pnpm 时可安装锁定版本：

```powershell
npm install -g pnpm@10.33.0
```

Docker Desktop 必须处于运行状态；`docker version` 应同时返回 Client 和 Server 信息。环境变量修改后重新打开终端。

## 4. 第一次启动：一步一步操作

### 第一步：拉取代码

第一次在新电脑准备项目时执行：

```powershell
cd D:\code
git clone https://github.com/280941478-blip/zs_yd.git cdzs-starter
cd D:\code\cdzs-starter
```

如果已经有 `D:\code\cdzs-starter`，直接进入现有目录，不要覆盖或重复克隆。后续命令都从这个根目录开始。

### 第二步：生成本地配置

```powershell
.\scripts\dev.ps1 init
```

执行后生成根目录 `.env`，自动创建随机数据库、Redis 和管理员初始密码。文件已存在时会保留原内容，不会重新生成密码。

可用编辑器打开 `.env` 查看配置。它包含真实密码，不要发到群里、写入文档或提交 Git。第一次本地运行通常无需改配置。

若 PowerShell 提示当前策略禁止运行脚本，可在当前终端临时允许运行本地脚本：

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy RemoteSigned
.\scripts\dev.ps1 init
```

公司设备由组织策略限制时，按公司的开发环境规定处理。

### 第三步：启动 MySQL 和 Redis

先打开 Docker Desktop，然后运行：

```powershell
.\scripts\dev.ps1 infra
```

等待脚本成功返回，再查看状态：

```powershell
docker compose --env-file .env -f deploy/compose.yml -f deploy/compose.dev.yml ps
```

MySQL 和 Redis 应为运行且健康状态。默认开发连接为：

| 服务 | 地址 |
|---|---|
| MySQL | `127.0.0.1:13306` |
| 数据库 | `cdzs_starter` |
| 数据库用户 | `cdzs` |
| Redis | `127.0.0.1:16379` |

密码读取根目录 `.env`。这些容器只映射到本机，不连接之前的采购系统数据库。

### 第四步：启动后端

新开一个 PowerShell：

```powershell
cd D:\code\cdzs-starter
.\scripts\dev.ps1 backend
```

脚本先 Maven 打包，再运行后端 JAR。首次需下载依赖，请保留终端运行。

第一次启动时会自动执行：

1. Flyway 创建基础表及初始化数据。
2. 创建示例任务表和菜单。
3. 设置管理员初始密码、默认文件访问地址和安装标记。

**不用手工导入 SQL，也不要再导入 `database/init/001-base.sql`。**

另一终端可以检查后端健康状态：

```powershell
Invoke-RestMethod http://localhost:48080/actuator/health
```

`status` 为 `UP`，且启动日志无失败异常，表示后端已启动。

### 第五步：启动前端

再开一个 PowerShell：

```powershell
cd D:\code\cdzs-starter
.\scripts\dev.ps1 frontend
```

脚本使用锁文件安装依赖，然后启动 Vite。终端显示可访问地址后打开：

```text
http://localhost:8080
```

登录信息：

| 项目 | 内容 |
|---|---|
| 租户 | 默认租户 |
| 账号 | admin |
| 初始密码 | 根目录 `.env` 的 `ADMIN_INITIAL_PASSWORD` |

验证码开启时，正常完成验证码后登录。进入系统后应看到新版工作台及系统管理、基础设施等菜单。

### 第六步：确认基础能力可用

- 打开“开发示例 → 示例任务”，新增一条自己的测试任务。
- 查询、修改、导出并验证自己的测试数据。
- 上传一个测试文件并下载。
- 查看登录日志。

到这里就可以开始业务开发了。

## 5. 使用 IDEA 开发后端

命令行启动适合快速验收；改 Java 代码时更适合用 IDEA 运行和调试。

### 5.1 导入 Maven 项目

1. IDEA 选择“打开”，选 `D:\code\cdzs-starter\backend\pom.xml`，作为项目打开。
2. 如果已经打开整个 `cdzs-starter`，在 `backend/pom.xml` 上右键，选择“添加为 Maven 项目”。不同 IDEA 版本名称可能略有不同。
3. 在“项目结构”设置 Project SDK 为 JDK 17。
4. Maven 设置中确认 Maven 路径、Importer JDK 和 Runner JRE；Java 使用 JDK 17。
5. Maven User settings file 可指定 `D:\code\cdzs-starter\deploy\maven-settings.xml`，与启动脚本使用的仓库镜像一致。
6. 重新加载全部 Maven 项目，等待依赖导入完成。

应能看到 `cdzs-server`、`cdzs-module-system` 等 Maven 模块，`src/main/java` 被识别为源代码目录。

不要导入 `.flattened-pom.xml`，它是构建生成文件。

### 5.2 配置启动项

创建 Application 或 Spring Boot 运行配置：

| 配置 | 值 |
|---|---|
| Main class | `cn.cdzs.server.CdzsServerApplication` |
| Use classpath of module | `cdzs-server` 对应主模块 |
| JRE | JDK 17 |
| Working directory | `D:\code\cdzs-starter\backend` |
| Active profiles | `starter`；若无该输入项，使用下面的程序参数 |
| Program arguments | `--spring.profiles.active=starter` |

工作目录设为 `backend` 时，后端会从 `../.env` 读取根目录配置。不需要把所有密码重复填到 IDEA 中。

先运行 `dev.ps1 infra`，再在 IDEA 点击运行或调试。若命令行后端还在运行，先在原终端按 `Ctrl+C`，避免两个后端同时占用 48080。

前端仍在单独终端运行 `dev.ps1 frontend`。改 Vue/CSS 后通常会自动热更新；修改前端环境文件后重启 Vite。

## 6. 配置文件说明

### 6.1 根目录 `.env`：后端和容器运行配置

| 参数 | 默认或来源 | 说明 |
|---|---|---|
| `COMPOSE_PROJECT_NAME` | `cdzs-starter` | Docker 项目名，影响容器和数据卷的分组 |
| `DB_NAME` | `cdzs_starter` | 数据库名称 |
| `DB_USER` | `cdzs` | 应用数据库账号 |
| `DB_PASSWORD` | 自动生成 | 应用数据库密码 |
| `MYSQL_ROOT_PASSWORD` | 自动生成 | 本项目 MySQL 容器的 root 密码 |
| `REDIS_PASSWORD` | 自动生成 | Redis 密码 |
| `ADMIN_INITIAL_PASSWORD` | 自动生成 | 首次安装使用，要求 12～16 位 |
| `DB_HOST` / `DB_PORT` | `127.0.0.1` / `13306` | 本机 Java 进程连接数据库的位置 |
| `REDIS_HOST` / `REDIS_PORT` | `127.0.0.1` / `16379` | 本机 Java 进程连接 Redis 的位置 |
| `APP_PUBLIC_URL` | `http://localhost:8080` | 首次初始化文件配置使用的访问地址 |
| `HTTP_BIND` / `HTTP_PORT` | `127.0.0.1` / `8080` | 全容器模式前端绑定地址和端口 |
| `API_DOCS_ENABLED` | `false` | 是否启用后端接口文档能力 |
| `STARTER_BASELINE_EXISTING` | `false` | 旧底座库接管专用，新项目保持 false |

重要区别：

- 管理员密码只在首次安装时设置。之后修改 `.env` 的初始密码，再重启，**不会修改数据库内已有用户的密码**。请在个人设置或用户管理中按权限修改。
- MySQL 已有数据卷时，修改 `.env` 的数据库密码也不会自动修改库内账号密码；需要配套执行账号密码变更，再同步应用配置。
- 修改 `COMPOSE_PROJECT_NAME` 会切换到另一组容器和数据卷，不是给原数据改名字。启动后看不到旧数据时先检查项目名。
- `APP_PUBLIC_URL` 不会每次覆盖已保存的文件配置。已有环境换域名后，到“基础设施 → 文件配置”同步更新实际访问域名。
- 全容器后端固定使用 Compose 内网的 `mysql:3306`、`redis:6379`，由 `compose.yml` 显式传入；根目录主机端口主要供本地开发使用。

### 6.2 前端配置

| 文件 | 用途 |
|---|---|
| `frontend/.env` | 公共标题、Vite 端口、租户开关等 |
| `frontend/.env.starter` | `pnpm dev` 的开发配置 |
| `frontend/.env.deploy` | `pnpm build` 的部署配置 |
| `frontend/vite.config.ts` | 开发接口代理，默认转发到 `127.0.0.1:48080` |

常改参数：

```dotenv
VITE_APP_TITLE=我的业务管理系统
VITE_PORT=8080
```

前端 `VITE_` 配置会进入浏览器产物，不可写入数据库密码、短信密钥或邮箱授权码。

本地前端端口由 `VITE_PORT` 控制；根目录 `HTTP_PORT` 控制 Docker 前端端口，两者不是同一个配置。

### 6.3 多项目端口示例

若同时运行第二个项目，创建独立目录和 `.env`，可采用：

```dotenv
COMPOSE_PROJECT_NAME=demo-project
DB_NAME=demo_project
DB_PORT=13307
REDIS_PORT=16380
HTTP_PORT=8081
APP_PUBLIC_URL=http://localhost:8081
```

本地开发还需要：

1. 在该项目前端设置 `VITE_PORT=8081`。
2. 第二个后端使用 `--server.port=48081`，或在该项目配置文件修改端口。
3. 将该项目 `vite.config.ts` 的 HTTP 和 WebSocket 代理目标都改成 48081。
4. 第一次创建容器前完成项目名、数据库名和密码配置。

如果用自己的外部 MySQL/Redis，本机运行后端可通过根目录参数连接；数据库应事先创建，使用独立库和账号。全容器或 Jenkins 模式不会自动改用外部服务，需要另外调整 Compose 的服务、连接配置和备份方案。

## 7. 每天如何启动与停止

完成第一次安装后，不需要再初始化数据库。

### 7.1 推荐开发流程

1. 启动 Docker Desktop。
2. 运行 `dev.ps1 infra`。
3. IDEA 启动后端，或执行 `dev.ps1 backend`，二选一。
4. 前端终端运行 `dev.ps1 frontend`。
5. 打开 `http://localhost:8080`。

已安装依赖且锁文件未变化时，也可直接：

```powershell
cd D:\code\cdzs-starter\frontend
pnpm dev
```

### 7.2 停止

- 命令行前后端：分别在对应终端按 `Ctrl+C`。
- IDEA 后端：点击停止。
- 数据库和 Redis：根目录执行：

```powershell
.\scripts\dev.ps1 stop
```

`stop` 只停止 Compose 容器，不停止独立运行的 Java、Vite 进程，也不会删除数据卷。

## 8. 全容器运行

适用于本地演示或验证完整部署形态。首次初始化仍需 Node；Java/Maven/前端构建工具在镜像内运行。

先停止独立运行的本机前后端，再在根目录执行：

```powershell
.\scripts\dev.ps1 all
```

该命令生成或保留 `.env`，构建镜像，启动 MySQL、Redis、后端、Nginx 前端并等待健康检查。首次需要网络下载镜像和依赖，耗时会较长。

成功后访问 `http://localhost:8080`。Compose 前后端改动需要重新构建；它不具备本地 Vite 的热更新方式。

检查状态和日志：

```powershell
docker compose --env-file .env -f deploy/compose.yml ps
docker compose --env-file .env -f deploy/compose.yml logs --tail 100 backend
docker compose --env-file .env -f deploy/compose.yml logs --tail 100 frontend
```

回到本地开发模式时先执行 `dev.ps1 stop`，再运行 `infra`、本机后端和前端。保持同一个项目名会继续使用原来的数据卷。

### Linux 对应命令

从项目根目录执行；前后端长期运行的命令需要分别开终端：

```bash
bash scripts/dev.sh init
bash scripts/dev.sh infra
bash scripts/dev.sh backend
# 另一个终端
bash scripts/dev.sh frontend
```

全容器与停止分别为：

```bash
bash scripts/dev.sh all
bash scripts/dev.sh stop
```

## 9. 登录后的基础配置

### 9.1 用户、组织与权限

建议顺序：部门 → 岗位 → 角色 → 用户 → 分配权限。

1. 在“系统管理 → 部门管理”建立实际组织。
2. 建立岗位和业务角色。
3. 新建用户，关联部门、岗位和角色。
4. 给角色分配业务菜单及按钮权限，按需设置数据范围。
5. 使用普通账号登录验收，检查菜单可见性及接口是否拒绝越权访问。

新业务必须主动接入数据权限。示例任务采用“本人数据 + 租户”隔离，不代表任意新表都自动拥有部门数据隔离。

### 9.2 文件上传与访问地址

默认文件内容存入数据库，可先上传一个测试文件验证。

部署到域名后：

1. 首次安装前将 `APP_PUBLIC_URL` 改为实际地址，例如 `https://admin.example.com`。
2. 如果已经初始化，进入“基础设施 → 文件配置”修改启用配置的访问域名。
3. 从实际访问网络测试下载，确认没有返回 localhost 或内网地址。

需要对象存储时配置自己的存储服务及凭据，并另外安排文件对象备份。

### 9.3 站内信、短信、邮件

| 类型 | 配置与验证步骤 |
|---|---|
| 站内信 | 新建模板 → 定义参数 → 测试发送给自己的后台用户 → 查看消息和已读状态 |
| 短信 | 创建云服务商签名/模板 → 配置底座渠道 → 对应服务商模板 ID 与参数 → 向指定测试号码发送 → 查看回执 |
| 邮件 | 配置 SMTP、端口、TLS/SSL、授权码 → 建立模板 → 向自己的测试邮箱发送 → 查看日志 |

后台用户接收站内信时选择管理员用户类型，填写真实用户 ID。模板测试成功只说明发送链路可用；业务事件触发发送仍需编写业务代码。

### 9.4 页面品牌与配色

- 系统名称：`frontend/.env` 的 `VITE_APP_TITLE`。
- 标识：同步替换 `frontend/src/assets/svgs/workspace-mark.svg` 与 `frontend/public/workspace-mark.svg`。
- 默认颜色：`frontend/src/store/modules/app.ts`。
- 公共组件样式：`frontend/src/styles/workspace.scss`。
- 登录页：`frontend/src/views/Login/Login.vue`。
- 首页：`frontend/src/views/Home/Index.vue`。

详见 [界面主题配置](界面主题配置.md)。

## 10. 从底座创建新项目

建议保留 `zs_yd` 作为团队底座，在独立仓库开发每个新业务项目。

一种方式是在 GitHub 将底座设为模板仓库，再从模板创建新仓库；这需要仓库管理员设置，当前教程不会自动修改仓库设置。

也可以克隆后切换远程地址：

```powershell
git clone https://github.com/280941478-blip/zs_yd.git my-project
cd my-project
git remote rename origin starter
# 将下一行替换为你自己已创建的新仓库地址
git remote add origin https://github.com/YOUR_ORG/my-project.git
```

这种方式保留底座历史和 `starter` 远程，方便之后对照升级；新业务应推送到自己的 `origin`。

每个新项目至少修改：

- 前端标题和品牌。
- 后端 `spring.application.name`。
- 根目录独立 `.env`：项目名、库名、密码和端口。
- `deploy/targets.json`：镜像项目、服务器、目录、凭据 ID。
- 自己的业务模块、菜单、权限和消息模板。

从 Git 克隆不会带来旧项目被忽略的 `.env`、依赖、日志、数据卷和备份，执行 `dev.ps1 init` 生成新的配置即可。保留上游许可证与版本来源。

## 11. 开发业务与数据库变更

### 11.1 在已建好的 business 模块中开发

| 内容 | 路径 |
|---|---|
| 后端 | `backend/cdzs-module-example/` |
| 前端接口 | `frontend/src/api/example/task/index.ts` |
| 前端页面 | `frontend/src/views/example/task/index.vue` |
| 示例表和菜单 | `backend/cdzs-server/src/main/resources/db/migration/V2__example_task.sql` |

开发一个新业务的一般顺序：

1. 定义业务表、字段、归属和权限范围。
2. 在 `backend/cdzs-module-business/src/main/java/cn/cdzs/module/business/` 下按领域分包，例如 customer。已有模块无需重复注册 Maven 依赖。
3. 编写 Controller、VO、Service 接口、ServiceImpl 实现、Mapper 和数据对象。Controller 注入 Service 接口，业务校验和事务写在 ServiceImpl。
4. 前端 API 放 `frontend/src/api/business/customer/index.ts`，页面放 `frontend/src/views/business/customer/index.vue`。
5. business 路由白名单已配置，菜单组件填写 `business/customer/index`，无需重复增加白名单。
6. 在菜单管理建立目录、页面和按钮权限，给角色授权。
7. 同时添加前端按钮控制和后端接口鉴权。
8. 用管理员、普通用户及不同数据归属进行测试。

例如按钮权限为 `crm:customer:create`，前端可用 `v-hasPermi`，后端必须配套 `@PreAuthorize`。仅隐藏按钮不能防止直接调用接口。

分层和目录详见 [业务模块开发约定](业务模块开发约定.md)，CRUD、导入导出和隔离逻辑参考 [标准业务模块开发](标准业务模块开发.md)。

首次启动后可进入“业务管理 → 业务首页”确认接入成功。它调用 `GET /admin-api/business/home/get`，权限为 `business:home:query`。默认租户管理员已初始化授权，其他角色需单独授权；菜单更新后重新登录。

只有需要拆分独立业务域时才另外创建 Maven 模块，并同步修改聚合 pom、启动模块依赖及前端路由白名单。

### 11.2 数据库使用增量版本 SQL

新增 SQL 放到：

```text
backend/cdzs-server/src/main/resources/db/migration/
```

例如当前已有 V1～V4，下一次可以新增：

```text
V5__add_customer_table.sql
```

版本号在团队中必须唯一，已执行过的迁移不能修改。改结构应新增后续版本；后端启动自动执行未执行的迁移。

不要编辑已执行的 V1～V4 来修改已有环境，不要删除 Flyway 历史记录来绕过失败。

### 11.3 旧底座库接管

仅针对这个底座在 Flyway 引入前创建的数据库：先备份，再临时使用 `STARTER_BASELINE_EXISTING=true`。验证迁移后恢复 false。

新库保持 false。已有采购系统或其他项目数据库不能直接套用该开关。

详见 [数据库版本管理](数据库版本管理.md)。

### 11.4 不需要日常执行的维护脚本

`configure-starter.cjs`、`generate-database.cjs`、`trim-frontend.cjs` 用于制作和维护基础版。普通开发不要重复运行，避免覆盖配置或重生成旧种子文件。

## 12. Jenkins 发布部署

Jenkins 是后续发版工具；本地开发无需先配置 Jenkins。

### 第一步：准备执行节点

使用 Linux 执行节点，标签为 `docker`，具备 Git、Docker Engine/BuildKit、Compose v2.24+、Bash、OpenSSH、tar。

安装流水线依赖插件：Pipeline、Git、Credentials Binding、SSH Agent、Pipeline Utility Steps、JUnit。编译在容器中进行，节点无需单独安装 Java、Maven 和 pnpm。

### 第二步：新建 Pipeline 任务

1. Jenkins 新建“流水线 / Pipeline”任务。
2. Definition 选择“Pipeline script from SCM”。
3. SCM 选择 Git。
4. 配置本项目或新业务项目的仓库 URL；私有仓库配置读取凭据。
5. 分支设为 `*/main`，或实际业务分支。
6. Script Path 填 `Jenkinsfile`。

不是新建旧式 Maven Project 任务。首次任务载入 Jenkinsfile 后才会注册其中定义的参数。

### 第三步：填写部署目标

编辑 `deploy/targets.json`：

| 配置 | 内容 |
|---|---|
| `registry` | 镜像仓库域名及团队命名空间 |
| `registryHost` | `docker login` 使用的仓库主机 |
| `registryCredentialId` | Jenkins 中的仓库凭据 ID |
| `project` | 该业务的镜像项目名 |
| `test` / `prod` | 各自 SSH 地址、用户、端口、部署目录、凭据 ID |

仓库里的 `CHANGE_ME` 和 `registry.example.com` 是占位配置，部署前需要替换。

### 第四步：配置凭据与服务器

| 默认凭据 ID | 类型 |
|---|---|
| `starter-registry` | 用户名与密码 / 仓库令牌 |
| `starter-test-ssh` | 测试服务器 SSH 私钥 |
| `starter-prod-ssh` | 生产服务器 SSH 私钥 |
| `starter-known-hosts` | 已核验指纹的 known_hosts Secret file |

服务器安装 Docker/Compose、Bash、flock；部署用户有对应目录和 Docker 权限，且服务器已登录私有镜像仓库。

在配置的部署根目录放置服务器专用 `.env`，权限设为 600。不要直接使用开发电脑的密码。测试和生产使用不同项目名、数据卷、目录与凭据。

填写实际 `APP_PUBLIC_URL`、`HTTP_BIND`、`HTTP_PORT`。同机使用 Nginx/1Panel 反向代理时，通常保留 `HTTP_BIND=127.0.0.1`，入口转发到 HTTP_PORT，并配置 HTTPS。

### 第五步：构建、测试环境发布、生产发布

| 参数 | 首次建议 | 含义 |
|---|---|---|
| `ACTION` | `BUILD_ONLY` | 先验证构建；正式推送部署选 `DEPLOY` |
| `TARGET_ENV` | `test` | 先测试，再 prod |
| `SCOPE` | `all` | 首次前后端一起发布 |
| `GIT_REF` | 留空 | 使用任务分支，也可指定分支或标签 |
| `ROLLBACK_VERSION` | 留空 | 回滚时使用，留空恢复上一成功版本 |

首次先执行 `BUILD_ONLY / all`；成功后执行 `DEPLOY / test / all`。验收通过后再发布生产。

已有环境后续可按需只更新 frontend 或 backend。流水线会构建、测试、推镜像、传输部署文件、启动服务、健康检查并记录版本。

远端镜像仓库、SSH、HTTPS 仍需在实际环境联调；本地验证通过不等于服务器已经配置完成。详见 [Jenkins部署](Jenkins部署.md)。

## 13. 备份与回滚

- 已有环境更新后端或全量发布前，自动备份 MySQL；备份失败则终止升级。
- 备份位于服务器部署根目录 `backups/`，默认成功备份后保留最近 14 天。
- Jenkins `ROLLBACK` 恢复应用镜像和对应部署配置，**不回退数据库**。
- 数据库迁移应兼容上一版应用；不能把应用回滚当成数据库恢复。
- 每日定时备份、异地备份需要按生产环境另外安排，当前底座没有替服务器自动创建每日计划。
- MySQL 备份不包含 `.env`、Redis 和外部对象存储文件，需分别规划。

正式覆盖恢复会删除并重建指定项目数据库，应先进行隔离恢复演练，并安排维护窗口。完整操作见 [部署备份与恢复](部署备份与恢复.md)，不要使用删除数据卷的方式处理普通启动问题。

## 14. 常见问题

### 修改了 ADMIN_INITIAL_PASSWORD，为什么登录还是密码错误？

已有管理员密码存放在数据库中，初始配置不会覆盖它。使用上次有效密码登录后修改，或通过有权限的管理员重置；不要为了改密码删除数据库。

### IDEA 里启动类没有运行图标，似乎没识别成 Java 项目？

先确认已导入 `backend/pom.xml`，Maven 同步成功，Project SDK 与模块 JDK 都为 17。不要只打开 Java 文件，也不要把生成的 `.flattened-pom.xml` 当作入口。

### 找不到 DB_PASSWORD，或者连不上数据库？

依次检查：根目录 `.env` 是否存在 → IDEA 工作目录是否为 backend → Docker 是否启动 → MySQL 是否 healthy → 主机端口和密码是否匹配。不要在日志中输出整份 `.env`。

### 8080 或 48080 被占用？

先检查是否同时运行了 IDEA、命令行和全容器版本：

```powershell
Get-NetTCPConnection -LocalPort 8080,48080 -State Listen -ErrorAction SilentlyContinue
```

根据 OwningProcess 确认所属进程，再正常关闭对应服务，不要直接结束不认识的进程。

### 登录页面能打开，接口却是 404 或 502？

本地模式检查后端 48080 是否启动、Vite 代理是否正确。容器模式检查 backend 健康状态、Nginx 日志和外层反向代理是否转发到当前项目。

### 修改了 frontend/.env 的标题或端口却没变化？

停止并重启前端。生产容器需要重新构建并发布前端镜像；环境变量不是运行后浏览器自动读取的服务器配置。

### 文件只能本机下载，其他人下载失败？

检查文件配置中是否仍为 localhost 或旧内网地址。已有数据库需从“基础设施 → 文件配置”调整域名，并确认入口反向代理允许对应下载路径。

### 新业务菜单有了，点击找不到页面？

检查后端菜单的组件路径、前端文件位置、`routerHelper.ts` 的 glob 白名单，以及当前角色授权。新增授权后重新登录刷新菜单缓存。

### Flyway 报校验失败？

检查是否修改了已经执行过的迁移文件。恢复原文件并用新版本 SQL 修正；先核实真实数据库状态，不要盲目 repair 或删除历史表。

### 数据突然像新安装的一样？

先核对 `COMPOSE_PROJECT_NAME`、数据库名、连接地址和 Compose 数据卷。很可能连到了另一套新库，不应立即重新导入旧 SQL。

## 15. 上线前检查

- [ ] 项目有自己的仓库、名称、数据库和环境配置。
- [ ] `.env`、密码、备份、日志没有提交到 Git。
- [ ] 默认管理员密码已妥善管理，普通账号权限已验收。
- [ ] 新业务接口有后端鉴权，租户和数据范围隔离已验证。
- [ ] 上传下载使用实际域名，短信/邮件使用正式渠道与模板。
- [ ] Jenkins 测试环境发布、健康检查和应用回滚已验证。
- [ ] 数据库备份可恢复，生产有独立备份计划。
- [ ] API 文档与扩展功能只按实际需要开放。
